# Built-in benchmark diagnostics

`LARECOMP_BENCHMARK=<scene file>` enables the harness; without it the counters, clocks and trace allocations are disabled. Scenes use scratch saves and scratch settings. `tools/benchmark-scenes.txt` documents the scene format.

Report format 2 adds a bounded cooling gate at the title before every scene/repeat: `thermal_max = 0..6` (Android thermal status, default -1 disables it), `thermal_wait_s = 1..3600` (default 300). An unavailable status or timeout gives `harness_error` at `cooling`, with elapsed wait and observed statuses. It does not silently proceed with a hot device. The title is still rendered while waiting.

Between scenes, a 60-second watchdog bounds the wait for guest threads to stop during reboot. A timeout writes `harness_error` at `reboot` and exits the run; it cannot safely reset guest memory while an old thread is still alive.

`frames.csv` includes title, arrival, camera, warmup and measured-window frames; `window=1` selects the latter. Cold-start activity is therefore retained without weakening the warmup. Every row has the 30 fps budget comparison and raw counter deltas. `report.json` aggregates measured-window rows only. `game_period_ms` (also the legacy `frame_ms`) is the game's present-to-present wall period, not a scanout interval. CPU work uses the existing pacer signal: game wall time minus kernel blocking, maxed with render work; it is not pure scheduled CPU time. GPU busy samples use the existing cumulative timestamp queries and are asynchronous estimates; a >100 ms hitch and its next frame have unknown GPU samples. Headroom is budget minus max(CPU,GPU); unknown input yields an empty CSV cell / no percentile sample, never zero.

Actual presentation timestamps come from `VK_GOOGLE_display_timing`. The present ID is joined to the game's exact handoff timestamp across the render queue. `display_period_ms` requires consecutive game frames, consecutive present IDs and monotonic actual timestamps. Window presentation percentiles require both endpoints in the window. Missing feedback stays empty and is counted; no CPU timestamp substitutes for scanout. The harness drains feedback for one second after the window. These extension timestamps describe Android presentation timing, not an independently measured panel scanout.

Counters record completed shader/program/pipeline jobs (worker elapsed time, possibly overlapping), blocking pipeline waits, CPU waits on the GPU timeline, CPU texture upload work (including decode), guest texture bytes uploaded, BC/ASTC CPU decode, and guest storage/file reads (count, successful bytes and elapsed time). BC render-target readback decodes are included. Upload duration includes decode: do not add them. File I/O on other guest threads and worker builds are correlations within the interval, not an exclusive critical-path decomposition. Operations spanning a boundary are charged to their completion interval; the first interval starts at benchmark boot. No counters are reset while workers run.

For each game period over 1000/30 ms, `likely_cause` chooses the largest measured stall covering at least 25% of the excess and 0.1 ms: pipeline wait, GPU wait above the window median, texture decode, upload excluding decode, or file read. Otherwise completed builds give `pipeline_activity` (correlation), then `unknown`. Raw values remain available for every category, so this heuristic cannot turn a coincident worker build into a proven blocking cause. Small pacing jitter also counts as over budget, with no hidden epsilon. Counts and raw counter totals are in each result's `long_frame_causes` and `window_counters`.

The cumulative relaxed-atomic counters and largest-stall / 25%-excess heuristic are adapted from [SavageWindRecomp](https://github.com/Revivedx/SavageWindRecomp/tree/257b1f3), `runtime/perfcount.h` and `tools/perf_routes.py`. This implementation uses an absolute frame budget instead of twice the median, includes BC decoding, gates collection behind the benchmark flag, and labels background compilation as activity.
